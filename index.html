Cómo usarlo

Una vez instalado (via /agent-system-core:init), las skills se invocan como slash commands normales. Ejemplos reales:

  • /feature-scaffolding HU-3055 — genera una feature CRUD completa (data-access + rutas + constants + list + form + i18n) a partir de una user story de Azure DevOps. Con --verify (/feature-scaffolding HU-3055 --verify) añade una fase de validación paralela (spec + código + tests + arquitectura) antes de implementar L6/L7.
  • /audit-module companies — auditoría completa de un módulo ya implementado: compliance contra las HUs asociadas (via component-feature-mapping.json), behavioral probes, cross-check con Figma, pattern compliance y generación de E2E spec. /audit-module companies --workflow lanza la variante fan-out con ~30 agentes en paralelo (probes P1–P6 + smoke-browser + síntesis). Sin argumentos (/audit-module o "revisa cambios") hace code review del diff actual (git diff <base>..HEAD).
  • /sync-models — compara los modelos TypeScript del frontend (*.model.ts, enums, tipos Search/Filter) contra los DTOs Java del repo de commons configurado en <BACKEND_REPO_PATH>, usando npm run check como punto de partida; propone una tabla de cambios y espera confirmación antes de editar nada.
  • /hu-refinement HU-3055 HU-3153 — refinamiento de sprint: lee las HUs de la wiki, inspecciona el módulo existente y devuelve una tabla de estimación por tasks (máx. 5 por HU) para planificación.
  • MCP servers: no se invocan directamente, los usan las skills anteriores. mcp__angular-cli__search_documentation / find_examples para consultar docs/API de Angular; mcp__primeng__get_component / get_component_props / list_examples / get_example para info y ejemplos de componentes PrimeNG. Ver bloque {{STACK_TOOL_PRIORITY}} más abajo para la política exacta de cuándo usarlas.

Configuración antes del primer uso (backend commons)

sync-models y el paso 7.5 (backend-crosscheck) de audit-module asumen un repo Java de "commons" hermano al frontend, como fuente de verdad de los DTOs. Estas rutas están parametrizadas con el placeholder <BACKEND_REPO_PATH> — la primera vez que uses cualquiera de estos dos skills en un proyecto nuevo:

  1. Clona (o localiza) el repo de commons del proyecto junto al frontend.
  2. Anota su ruta real en .claude/agent-system.config.json (o dile a Claude la ruta la primera vez que invoques /sync-models; puede guardarla en canonicalExamples para no repetirla).
  3. Del mismo modo, backendBaseUrl en las specs de feature-scaffolding usa ${environment.apiGw.<API_GW_KEY>.url} como plantilla — sustituye <API_GW_KEY> por la clave real de environment.apiGw.* de tu proyecto (revisa src/environments/environments.ts).

Si tu proyecto no tiene un repo de commons Java separado, sync-models y el paso 7.5 de audit-module no aplican: puedes ignorarlos o quitar la regla self-learning-error-prevention asociada.

Notas

Skills genéricas (skills/)

  • spec-driven-dev — ciclo obligatorio Spec → Plan → Build → Test → Review → Ship con puertas de aprobación humana; se usa para cualquier feature/refactor no trivial que toque más de un fichero.
  • debug-hypothesis — fuerza el método científico (Observar→Hipotetizar→Experimentar→Concluir) al depurar bugs no obvios, en vez de "probar cosas" a ciegas.
  • refactor — flujo de refactor multi-fichero: mapear el radio de impacto, proponer enfoque, confirmar, implementar en lotes verificando build tras cada uno.
  • typescript-best-practices — guía extensa de tipado, manejo de errores, patrones de arquitectura y organización de código TypeScript (incluye scripts de análisis/scaffolding y presets de tsconfig).
  • playwright-best-practices — referencia muy amplia (30+ documentos) de testing E2E/componentes/API con Playwright: locators, fixtures, CI/CD, mocking, accesibilidad, flaky tests, frameworks (Angular/React/Vue/Next), etc.

Además, el plugin trae skills de soporte interno que usan los propios agentes/comandos (no pensadas para invocación manual directa, salvo la última):

  • agent-evolution — usada por el agente evolver para auditar una sesión multi-agente contra un catálogo de antipatrones.
  • self-learning-error-prevention — implementa el loop SCAN→LEARN→PROMOTE→DECAY del knowledge-log (errores aprendidos LE-...); se activa al empezar tareas, tras arreglar bugs, y cuando el hook Stop exige auditoría.
  • save — la que ejecuta realmente /agent-system-core:save, lanzando al agente wiki-saver.
  • documentation-writer — experto en documentación técnica siguiendo el framework Diátaxis; disponible para redactar documentación de calidad cuando se necesite.

Concepto de "preset de stack"

dev-agent-system-core es el motor genérico: agentes, hooks, comandos y skills que funcionan en cualquier proyecto, sin saber nada de un framework concreto. No incluye reglas de arquitectura de Angular, .NET o Java.

Los plugins hermanos son presets de stack que se instalan *encima* de este motor y aportan lo específico de una tecnología:

  • dev-agent-system-angular — reglas de arquitectura Angular 20+/PrimeNG/Tailwind/NgRx Signal Store, feature-scaffolding, audit-module, sync-models, MCP servers (angular-cli, primeng).
  • dev-agent-system-dotnet — reglas de capas/módulos, EF Core, JWT/Keycloak, manejo de errores; skills de scaffolding/auditoría/migraciones/pre-commit.
  • dev-agent-system-java — arquitectura de dos paquetes (librería compartida + proyecto), seguridad Keycloak/OAuth2 multi-tenant, persistencia JPA/Specification, skills de scaffolding/auditoría/tests-gated-por-spec.

Los tres declaran explícitamente Requiere dev-agent-system-core en su descripción del marketplace, y todos exigen sustituir placeholders propios del proyecto antes del primer uso (ver el README de cada preset).

El punto de conexión entre ambos es la Fase 5 de /agent-system-core:init: si detecta (o el usuario confirma) que hay un preset instalado, init copia las rules/ y rules-on-demand/ de ese preset al proyecto como base editable, añade sus scripts si se desea, y las registra en agent-system.config.json (rules.alwaysOn/rules.onDemand) y en los placeholders {{STACK_TOOL_PRIORITY}}/{{STACK_SECTION}} del CLAUDE.md generado.

Cómo instalarlo

Instala el plugin dev-agent-system-core desde el marketplace attrim-marketplace con el flujo habitual de plugins de Claude Code (marketplace ya añadido → /plugin install dev-agent-system-core@attrim-marketplace o equivalente desde el gestor de plugins). Si el proyecto usa Angular, .NET o Java, conviene instalar también el preset de stack correspondiente (dev-agent-system-angular, dev-agent-system-dotnet o dev-agent-system-java) antes o justo después de ejecutar /agent-system-core:init, para que la Fase 5 del instalador lo detecte y lo aplique automáticamente.

Cómo usarlo

1. Inicializar un proyecto nuevo

/agent-system-core:init

Detecta el stack (package.json, angular.json, linters, test runner…), hace un máximo de 2 tandas de preguntas sobre lo que no pudo inferir (comandos de build/lint/test, rama base, carpetas canónicas, iniciales para IDs de errores aprendidos, y si aplicar un preset instalado), y deja el proyecto operativo: .claude/agent-system.config.json, CLAUDE.md, reglas en .claude/rules/, seeds de wiki en docs/wiki/, y una propuesta de settings.json (que siempre se muestra como diff antes de escribir). Nunca sobrescribe wiki/knowledge-log/agent-memory existentes sin confirmación.

2. Invocar a un agente concreto

Por ejemplo, pedir al architect que planifique una feature antes de tocar código:

> "Actúa como el agente architect y planifica cómo estructurar un módulo de facturación con listado, alta y edición, reutilizando los componentes canónicos del proyecto."

El architect lee primero agent-system.config.json y las reglas alwaysOn, propone estructura de carpetas/ficheros, modelos de datos y patrón de estado — pero no escribe código funcional (eso lo hace después el agente dev).

O pedir al reviewer que audite lo último hecho:

> "Que el agente reviewer revise los cambios del último commit contra las convenciones del proyecto y me dé feedback."

El reviewer analiza el git diff reciente, marca los patrones repetidos como el problema principal (no el más fácil de arreglar primero), y responde en Markdown con fichero/línea/motivo/sugerencia — sin editar nada él mismo.

3. Cerrar la sesión (auto-evolución y wiki)

Al terminar una sesión de trabajo donde se editaron ficheros y aparecieron señales de bug, el hook Stop (stop-self-evolve.sh) detecta esas señales en el transcript y bloquea el cierre con una directiva G:EVOLVE AUDIT REQUIRED: obliga a revisar si hubo un error no trivial resuelto y, si es generalizable, proponer una entrada nueva en el knowledge-log (LE-<INICIALES>-NNN) antes de continuar. Independientemente de eso, si la conversación produjo conocimiento valioso, se puede archivar explícitamente con:

/agent-system-core:save nombre-de-la-decision

que lanza al agente wiki-saver, el cual escribe docs/wiki/outputs/nombre-de-la-decision.md con frontmatter completo (tipo, confianza, tags, fuentes) y hace git commit (o avisa si el commit está denegado en settings.json).

Requisitos / configuración previa

  • El proyecto debe tener .git/ (o confirmarse como raíz) para que /agent-system-core:init pueda funcionar con normalidad (diffs, canonicalExamples, etc.).
  • El flujo de orquestación multi-agente (architect → dev → tester → reviewer) depende de que settings.json tenga CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: true — init lo propone en la Fase 7, salvo que la versión de Claude Code ya soporte agent teams de forma nativa.
  • Los hooks de lint/format esperan oxfmt/prettier y oxlint/eslint/ruff en node_modules/.bin/ o en el PATH (autodetección); si el proyecto usa otra herramienta, hay que configurar hooks.postEdit.format/lint explícitamente en agent-system.config.json.
  • Los hooks son scripts Bash (compatibles con Git Bash en Windows, según comentario en stop-self-evolve.sh) y dependen de node disponible en el PATH para parsear JSON.
  • Sin .claude/agent-system.config.json (es decir, sin haber corrido /agent-system-core:init en ese proyecto), los tres hooks y la mayoría de agentes salen en silencio o degradan su comportamiento — el plugin no rompe proyectos no inicializados, pero tampoco aporta valor hasta que se inicializan.

Notas relevantes

  • Los agentes architect y reviewer tienen prohibido explícitamente escribir/editar código (!!writes_functional_code / !!direct_code_edit) — son puramente de planificación y auditoría; solo dev y debugger tienen Edit/Bash para modificar el proyecto.
  • El agente evolver tiene una guardarraíl de auto-protección: nunca se analiza ni se edita a sí mismo ni a su propia skill (agent-evolution), y cualquier propuesta suya sobre el propio motor del plugin (agentes/hooks/skills de dev-agent-system-core) se marca como "PROPUESTA UPSTREAM: PR al repo del plugin", no como un diff local a aplicar.
  • El hook post-edit-lint.sh nunca bloquea (exit 0 siempre) — solo imprime violaciones para que se corrijan en el mismo turno, no interrumpe el flujo del agente.
  • El hook stop-self-evolve.sh sí puede bloquear el cierre de turno (decision: block) cuando detecta señales de auto-aprendizaje sin auditar; se desbloquea escribiendo .claude/state/audit-<session_id>.done tras completar la auditoría descrita en la skill self-learning-error-prevention.
  • Aunque la descripción del marketplace lista 5 skills "genéricas", el plugin trae 4 skills adicionales de soporte interno (agent-evolution, self-learning-error-prevention, save, documentation-writer) que sostienen el ciclo de auto-aprendizaje y los comandos — no son casuales, forman parte del mecanismo, aunque no se invocan manualmente salvo documentation-writer.

Cómo usarlo

Una vez instalado (tras /agent-system-core:init y sustituir los placeholders), las skills se invocan como comandos dentro de una sesión de Claude Code. Ejemplos reales de flujo completo:

  • Crear un módulo nuevo de punta a punta (feature-scaffolding → create-migration → pre-commit-validate):
  /new-module Invoice "number:string amount:decimal issuedAt:DateTime" --public --sync-a
  /create-migration AddInvoice
  /validate

El primer comando genera entity, DTOs, service+mock, controller(s) y registros DI del módulo Invoice (con controller público además del interno, y sincronización con el provider A); el segundo genera la migración EF Core correspondiente (con el guardarraíl de detección de cambios destructivos); el tercero da el veredicto READY TO COMMIT | BLOCKED antes de cerrar la tarea.

  • Añadir un endpoint a un recurso ya existente:
  /add-endpoint InvoiceController "marcar una factura como pagada"

Añade el método al servicio (con mock guard y XML docs), el endpoint al controller con la paridad Public/Internal que corresponda, y los tests happy-path/mock-path/not-found.

  • Auditar consistencia antes de una PR grande:
  /sync-check Invoice

o sin argumento (/sync-check) para auditar todo el backend: revisa paridad Public/Internal, completitud de provider-sync, DI sin duplicados, tests y mock guards, y reporta findings [ERROR]/[WARNING]/[OK] por fichero:línea sin modificar nada.

  • Generar una migración suelta tras cambiar una entidad a mano:
  /migrate RenameInvoiceStatus

Cómo usarlo

Flujo básico de sesión:

  2. Trabajas normalmente en la tarea (features, decisiones, feedback que le das a Claude sobre cómo abordar el proyecto).
  3. Al terminar la sesión, ejecuta /wrap-up (opcionalmente con una nota breve, ej. /wrap-up terminada la migración de auth). El comando mira el git diff de la sesión, actualiza las memorias de tipo project/feedback/user/reference que correspondan y guarda un snapshot en .claude/memory/sessions/.

Traspasar una tarea a un compañero:

  • Si vas a dejar una tarea a medias para que la continúe otro miembro del equipo (o tú mismo en otra máquina), ejecuta /handoff continuar la migración de auth a signals. Como .claude/memory/ está fuera de git, ese archivo no viaja con un git pull — hay que compartirlo aparte (Slack, copiar el contenido, etc.).

Consultar y corregir la memoria a mano:

  • Para ver qué hay guardado sin abrir archivos uno a uno: /memory-status. Lista las memorias agrupadas por tipo, cuántos snapshots hay (de un máximo de 5) y qué handoffs quedan pendientes.
  • Si una memoria quedó obsoleta o es incorrecta (por ejemplo, menciona una rama ya cerrada), corrígela con /memory-forget rama feature/auth-antigua. El comando busca coincidencias, pide confirmación si hay ambigüedad, y borra o actualiza el archivo según lo que se le pida.

Requisitos / configuración previa

  • No requiere configuración ni dependencias externas: los comandos solo usan herramientas estándar (Read, Write, Edit, Glob, Bash).
  • La memoria se guarda siempre en .claude/memory/ dentro del repo del proyecto actual, nunca en ~/.claude ni en rutas absolutas de usuario/máquina.
  • .claude/memory/ debe estar en el .gitignore del proyecto — el propio plugin añade esa entrada automáticamente la primera vez que se usa, si no está ya. Es memoria local del proyecto (y de quien la generó), no memoria de equipo: nunca se commitea ni se propone en un PR.

Notas relevantes

  • /wrap-up y /handoff son complementarios, no equivalentes: /wrap-up guarda contexto acumulativo y tipado para que tú mismo lo retomes en una sesión futura (vía /start); /handoff genera un documento suelto, de un solo uso, para entregar a otra persona sin acceso a tu historial de conversación.
  • Como los handoffs quedan fuera de git, compartirlos con un compañero requiere un paso manual (Slack, pegar el contenido, etc.) — no basta con que el compañero haga git pull.
  • /handoff redacta explícitamente datos sensibles (claves, contraseñas, tokens, datos personales) antes de guardarlos en el documento de traspaso.
  • Los snapshots de sesión están limitados a 5: al crear uno nuevo por encima del límite, /wrap-up borra automáticamente el más antiguo.

Plugin de Claude Code que genera la descripción de una Merge/Pull Request a partir del diff de la rama actual, filtrando lo que de verdad le importa a un reviewer.

Qué incluye

El plugin trae un único comando:

  • /explain-this-branch [rama-base opcional, default develop] [--azure=<ID>]

Comportamiento por defecto (modo MR)

Sin ningún flag, el comando:

  1. Determina la rama base (el argumento que se pase, o develop por defecto; si el proyecto no usa develop, se confirma con el usuario si usar main/master).
  2. Analiza los cambios con git log <base>..HEAD --oneline y git diff <base>...HEAD --stat (solo baja a diffs de ficheros concretos si el log/stat no bastan para entender la intención).
  3. Aplica un filtro de valor para el reviewer: solo entra lo que cambia cómo revisa o qué debe vigilar (contrato de API, migraciones, cambios de arquitectura, seguridad, breaking changes, zonas de riesgo). Fuera lint, formato, imports reordenados, tests que solo acompañan al código, documentación interna o tooling del agente (.claude/*, .agents/*).
  4. Agrupa los cambios por módulo/funcionalidad (nunca commit por commit ni archivo por archivo) y, solo si aporta, usa un diagrama mermaid, una tabla antes | ahora o un bloque <details>.
  5. Emite el resultado como un bloque de código markdown copiable directamente en el chat, listo para pegar en la descripción de la MR. No crea ficheros ni hace commits.

Es agnóstico de stack: el análisis se basa en git log/git diff, no en leer el código fuente del proyecto.

Los cambios sin commitear (working tree) se ignoran por defecto; solo se incluyen si el usuario lo pide expresamente, marcados como "pendiente de commit".

Modo Azure DevOps opcional (--azure=<ID>)

Si se añade --azure=<ID> (o se pide en lenguaje natural, p. ej. "publícalo en la HU 1099"), el comando genera además un segundo texto, más técnico, orientado a trazabilidad (endpoints afectados, DTOs/tipos, resumen técnico de implementación, migraciones), y lo publica como comentario en ese work item de Azure DevOps.

Este modo es aditivo: no sustituye la descripción de la MR, se genera después y reutiliza el mismo análisis git. Es aquí donde el plugin deja de ser agnóstico de stack: los patrones de extracción de endpoints y DTOs se adaptan al framework del proyecto (Spring, .NET, NestJS, Express/Fastify, etc.).

Antes de publicar, siempre se muestra el texto exacto en el chat y se pide confirmación explícita — nunca se publica sin ella.

Cómo instalarlo

Cómo usarlo

Ejemplo 1 — uso normal, sin Azure

/explain-this-branch

Compara la rama actual contra develop, analiza commits y diff, y devuelve en el chat un bloque markdown copiable con ## ¿Qué incluye esta MR?, ### Cambios principales y (si aporta) ### Notas para el reviewer. También se puede indicar otra rama base explícitamente:

/explain-this-branch main

Ejemplo 2 — con --azure=<ID>, pidiendo confirmación antes de publicar

/explain-this-branch develop --azure=1099

Genera primero la descripción de la MR como en el ejemplo 1 y, a continuación, construye el resumen técnico para la HU 1099 (endpoints afectados, DTOs/tipos, resumen técnico, otros cambios relevantes) y lo muestra en el chat en una previsualización, preguntando algo como "¿Confirmas que publique este comentario en la HU #1099?". Solo tras una respuesta explícita ("sí", "confirma", "adelante"...) ejecuta el script de publicación; un silencio o un mensaje ambiguo no se interpreta como confirmación. Si se pide un cambio en el texto, se ajusta y se vuelve a mostrar antes de publicar.

También se puede pedir en lenguaje natural sin usar el flag: "explica la rama y publícalo en la HU 1099".

Notas relevantes

  • Seguridad del PAT: el AZURE_PAT nunca se hardcodea en el script, en la conversación ni en ningún fichero del repo — siempre se lee de process.env. La skill tiene instrucción explícita de no aceptar ni pedir un token pegado en el chat.
